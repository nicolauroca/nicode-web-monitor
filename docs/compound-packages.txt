Compound packages - development boundary, 30 October 2026

The inventory now includes package_id for each extension. The panel shows the
extension ID and Package ID. None means Joomla recorded zero; Unknown means the
collector did not provide a usable value. Compare IDs only within the same site.
An orphan has package_id=0 too: None does not prove a healthy standalone install.

Read-only diagnosis from a local checkout, using the site's PHP environment:
php tools/inspect_package.php /path/to/joomla pkg_example

This lists the parent registry row and linked children. To find replacements
that lost their package relation, supply an optional UTF-8 JSON file containing
the expected child identities, taken from the trusted package manifests:
[{"type":"library","element":"example","folder":"","client_id":0}]
php tools/inspect_package.php /path/to/joomla pkg_example identities.json

Missing parents/children produce empty arrays, not an installation verdict.
Duplicate identities remain visible. No params, credentials, update URLs, SQL,
filesystem paths or raw manifest contents are returned. This is a registry and
version observation; it does not verify file integrity or establish recoverability.

Local implementation boundary
PackageOperation is a local primitive for a locally bound, trusted installer.
Its caller MUST hold the shared MaintenanceGate under extension:OPERATION,
stop writers, put the disposable/site environment offline and verify recovery
before installation. The target set must match the complete installed child set;
adding/removing children and downgrades are not supported by this primitive.
Before/after snapshots retain actual IDs, including library replacements.
All target versions and parent/child ownership must match before marking updated.
The durable started receipt precedes effects. False returns, exceptions, lost
processes, missing/extra/orphaned children and failed observation remain uncertain.
The same operation never reinstalls. A reused ID with a different plan is rejected.
The shared gate remains held on uncertainty. There is no automatic rollback,
retry, gate reset or claim that a registry snapshot is a backup.

Native reproduction on an isolated Joomla 6.1.4 / PHP 8.4.26 / MariaDB laboratory:
install package 1.0.0 containing library and module; update both to 1.1.0;
then update to 1.2.0 while rejecting the module in its preflight script.
The second update leaves library 1.2.0 with a NEW ID and package_id=0, while
the parent and module remain at 1.1.0. Native installation does not restore the
first child. The observation includes the orphan by identity and the journal
preserves this mixed state as uncertain. Another maintenance owner is rejected.

Remote compound-package updates are integrated in the development connector as

Package-owned standalone libraries remain rejected. This is not release acceptance.

Local archive inspection and preparation (30 October, evening)
Use a trusted package obtained separately. Hashes bind bytes; they do not prove
publisher authenticity or make installer scripts safe. Use the site's PHP CLI
with ZIP and SimpleXML enabled. From a checkout:
php tools/inspect_package_archive.php /private/package.zip EXPECTED_SHA256

The report contains the parent element/version, every declared child's complete
identity and version, child ZIP SHA256 values and the outer ZIP SHA256. All ZIPs
are inspected without extraction or script execution. Temporary child archives
are deleted. Parent plus child expanded data share a 128 MiB inspection budget;
each archive has at most 10,000 entries, with at most 32 children. Paths, collisions,
special files, encryption, entity declarations, ambiguous root manifests, missing
or duplicate children and declaration/manifest identity conflicts fail closed.
Supported structure: canonical root package manifest and root-level child ZIPs
of plugin/module/component/template/library types. Nested package ownership and
files-folder layouts are rejected, not silently flattened or partially accepted.
Passing inspection does not predict installer script success or guarantee rollback.

For a disposable rehearsal, first install the previous package, put Joomla offline,
stop independent writers and independently verify recovery. Create a private
directory outside and not containing the web root. Then:
php tools/prepare_package_update.php /path/to/joomla /private/compound /private/package.zip unique-operation-id --writers-stopped-and-recovery-verified

The command reads the native registry and requires the exact complete child set,
ownership and non-protected rows. A newer parent and no child downgrades are
required. Adding/removing children remains unsupported. It copies the archive,
re-inspects that copy and rechecks the installed baseline before writing a durable
15-minute compound-package-v1 permit. Existing operation directories/receipts
are never overwritten. Failed preparation can leave a reserved directory without
a permit; preserve it and investigate, rather than reusing its operation ID.
This is preparation only: no maintenance gate is acquired or installation performed.
Register the prepared operation ID in the panel, then confirm execution explicitly.
The consumer revalidates kind/expiry/copy/baseline under the shared maintenance
gate and uses PackageOperation. Status reads remain available after permit expiry.
Lost responses are reconciled by GET; the panel never resends uncertain operations.
